01整体架构分析

GBrain 是一个「契约优先（contract-first）」的分层系统：一份共享的 Operations 契约同时生成 CLI 与 MCP 两套表层；下方是可插拔的双存储引擎；旁挂一个可嵌入二进制的 React 管理前端。所有组件围绕一个不可变的核心不变量集合协作。

1.1 分层总览 #

系统自上而下分为五层：接入层（Agent / 终端 / 浏览器）、表层（CLI、stdio MCP、HTTP MCP、Admin SPA）、契约层（operations.ts — 单一事实来源）、核心服务层（检索、图谱、Minions 任务队列、Dream Cycle、AI 网关）、存储层（BrainEngine 抽象之下的 PGLite 或 Postgres+pgvector）。

1.2 Contract-First 设计模式 #

整个系统最核心的架构决策是：CLI 与所有 MCP 传输都不是手写的，而是从 src/core/operations.ts 导出的 operations: Operation[] 数组「运行时迭代」生成的——没有代码生成步骤，只有对同一数组的遍历。这消除了「加了一个 CLI 命令却忘了加 MCP 工具」这类漂移。

每个 Operation 是一条自描述记录：

export interface Operation {
  name: string;
  description: string;
  params: Record<string, ParamDef>;        // 类型化参数 schema
  handler: (ctx, params) => Promise<unknown>;
  mutating?: boolean;
  scope?: 'read'|'write'|'admin'|'sources_admin'|'users_admin';  // 远程鉴权
  localOnly?: boolean;                       // 永不暴露给远程传输
  cliHints?: { name?; aliases?; positional?; stdin?; hidden? };  // CLI 生成提示
}
  • CLI 生成（src/cli.ts）：构建 cliOps: Map<string,Operation>，以 cliHints.name 为键；positional 映射位置参数、stdin 读取管道输入。
  • MCP 工具生成（src/mcp/tool-defs.ts）：buildToolDefs(operations) 用同一个 paramDefToSchema() 把 ParamDef 递归映射为 JSON Schema。三处调用点（stdio、HTTP tools/list、subagent 工具注册）共享此 mapper，因为它们曾经漂移过。
  • 统一分发（src/mcp/dispatch.ts）：dispatchToolCall() 是所有传输的唯一漏斗——解析 op → validateParams → 构建 OperationContext → 调 handler → 序列化为 MCP 信封。它的存在就是为了防止 stdio / HTTP 漂移。

1.3 组件依赖关系 #

下图展示 src/ 主要模块间的依赖方向。注意 operations.ts 处于中枢：表层依赖它，它依赖 engine.ts 抽象与核心服务；引擎工厂通过动态 import 保证 PGLite 的 WASM 永不为 Postgres 用户加载（反之亦然）。

1.4 前端架构（Vite + React） #

admin/ 是一个 Vite 6 + React 19 + TypeScript SPA，刻意与上游隔离（admin/tsconfig.json 只 include: ['src']，无法 import ../../src/core/*）。它不使用 Router 库，而是基于 hashchange 的路由。前端呈现双表层：暗色的运维「驾驶舱」（Ops）与浅色的知识阅读界面（Brain）。构建产物 admin/dist/ 通过 src/admin-embedded.ts 以 import ... with { type:'file' } 嵌入二进制，使 gbrain serve --http（默认端口 3131）能在编译后的单文件二进制里服务 /admin。详见 §6 MCP 集成 与 §3 核心功能。

五条跨切面不变量（must-never-violate）
  • 信任 fail-closed：OperationContext.remote 必填；非严格 false 即视为远程/不可信。
  • Source 隔离：所有读侧 op 经 sourceScopeOpts(ctx)，杜绝跨源数据泄露。
  • JSONB 铁律：永不 JSON.stringify 进 ::jsonb（postgres.js 会双重编码；PGLite 掩盖此 bug）。
  • 引擎对等（parity）：新方法/SQL 形状必须同时落到两个引擎，由 engine-parity.test.ts 钉死。
  • 契约优先：operations.ts 单源，CLI+MCP 生成；每个 op 携带 scope + 可选 localOnly。

02设计理念与思想

GBrain 的一句话哲学：「搜索给你原始页面，GBrain 给你答案。」 它要成为「记忆领域的下一个 Postgres」——最经得起测试、覆盖面最广、以最低成本服务最多人的检索 + Agent 记忆系统。

2.1 北极星（North Star） #

搜索 vs 大脑

多数个人知识系统给你「10 个提到关键词的 chunk」。GBrain 额外提供两样别人不同时具备的东西：

  • 合成层：跨人物/公司/交易/想法的、带引用的合成散文，并显式标注「大脑还不知道什么」（gap analysis）。
  • 自织知识图谱：每次页面写入都以零 LLM 调用抽取实体引用、创建类型化边（works_at、invested_in、founded、advises、attended）。

Benchmark（BrainBench）

在 240 页 Opus 生成的富文本语料上：P@5 49.1%、R@5 97.9%；相比其「图谱关闭」变体 +31.4 分 P@5，相对 ripgrep-BM25 + 纯向量 RAG 也有相近幅度领先。「gbrain 最好」是一个整系统命题——由完整 BrainBench 套件证明，而非任一单点特性。

2.2 「守护进程 > 聊天」的思想 #

作者的核心洞察：「让一个 24/7 运行的守护进程去入库、增强、整合，比让一个 Agent 在聊天里持续苦干更容易。」 GBrain 就是这个被泛化的守护进程——夜间自动摄取会议、邮件、推文、语音、原创想法；增强遇到的每个人和公司；修复自己的引用；整合记忆。护城河是那个 10 万页的大脑；大脑层让护城河可用；Dream Cycle让它保持锋利（见 附录 · Dream Cycle）。

2.3 实体-状态设计法（四问设计法） #

本 fork 内置了一套贯穿的方法论（.qoder/skills/entity-state-design/）：系统存在的本质目的是跨越时间与空间传递信息；所有数据归根结底是在记录「某实体在某时刻的状态快照」。 设计时不从「用户要什么功能」出发，而从「我要管理哪些实体、它们的哪些状态需要通过什么流程传递给谁」出发。功能只是状态变更的实现手段。

该方法与 GBrain 自身设计高度自洽：pages 是核心实体，deleted_at/generation/links_extracted_at 是其状态；minion_jobs.status 是一台严格的状态机（见 §3.3）；facts/ontology 用双时序（bi-temporal）字段记录状态随时间的迁移与 supersession。

2.4 设计系统与「声音」 #

面向用户的文案有明确「声音」规范（DESIGN.md）：「像一个了解你过去的聪明朋友，而不是临床评分系统。」 第二人称、允许缩写、用可验证的具体数据（「3 个里漏了 2 个」优于「Brier 0.31」）、不说教、25 词以内。五个面（pattern_statement、nudge、forecast_blurb、dashboard_caption、morning_pulse）均经 gateVoice() 用 Haiku 裁判过滤学术腔，最多 2 次重生，再回退到手写模板。

03核心功能特性

四大核心功能：内容入库（ingest / Inbox）、知识检索（query / think）、Minions 任务队列、实时监控。它们由契约层暴露，由核心服务实现，并被 Dream Cycle 编排为夜间自治流程。

3.1 内容入库（Ingest / Inbox 工作流） #

写入路径 put_page 是一个「写后即织」的重型操作：分块（chunk）→ 嵌入（embed）→ 协调标签 → 零 LLM 抽取类型化链接 → 抽取时间线条目。链接抽取是一次完整协调（reconciliation）（非追加）：在 slug 哈希的咨询锁（pg_advisory_xact_lock）内运行，删除陈旧边、保留 link_source='manual' 的手工边、且所有读写都串上 sourceId 以防跨源幻删。

本 fork 额外引入 Inbox 入库工作流：inbox/* 页有一套 frontmatter 状态机（pending_frontmatter → pending_typed_link → merging → merged），配 4 个契约 op（list_inbox、get_inbox_item、trigger_inbox_enrichment、discard_inbox_items）与一个零 LLM 确定性 enrichment handler（inbox_enrich），批量增强不烧 token。

3.2 知识检索（Query / Think） #

search / query — 原始检索

search 是纯关键词 FTS；query 是混合检索（向量+关键词+关系+图），带多查询扩展、autocut、adaptive_return。返回排序好的页面/chunk，无 LLM 成本（除非开启扩展）。本 fork 为 query 增加可选 trace:true，返回 {results, trace} 供 Ask 页做检索诊断瀑布图。

think — 合成层

多跳合成：拉取相关证据（页面+takes+图），产出带引用的散文答案 + 冲突分析 + gap 分析。这是「大脑 vs 搜索」的分水岭。远程调用者的 --save/--take 被禁用（信任边界）。

检索机制的完整内部实现见 §5 搜索与检索机制。

3.3 Minions 任务队列 #

Minions 是 GBrain 的后台作业系统，落在 minion_jobs 表（一台严格状态机）。作业按执行通道（execution lane）分类（纯函数 getExecutionLane(name)，永不与 worker.register() 漂移）：

Lane触发名含义
shellshell临时 shell 作业（CLI-only，MCP 拒绝）
subagentsubagent, subagent_aggregatorLLM 编排的子 Agent 作业
handlersync, embed, extract, synthesize, inbox_enrich …确定性 handler

作业状态机（src/core/minions/queue.ts）：终态为 completed / failed / dead / cancelled；父作业等待子作业时进入 waiting-children；预算耗尽时子树被翻为 dead(budget_exhausted)。

队列具备生产级韧性：租约（rate-leases）、背压审计（backpressure-audit）、静默时段（quiet-hours）、niceness 优先级、锁续约心跳（lock-renewal-tick）、子进程监督（child-worker-supervisor）、幂等键、超时看门狗。任务管理 op 共 11 个（submit_job、get_job、cancel_job、retry_job、pause_job、resume_job、replay_job、send_job_message 等，见 §11）。

3.4 实时监控 #

Admin SPA 混用 SSE + 轮询（无 WebSocket）。服务端 GET /admin/events 是一个全局请求活动流：每条 MCP/admin/webhook 请求经 logMcpRequest 广播一帧 {agent, operation, scopes, latency_ms, status}，每 25s 一次心跳 ping 防代理空闲超时。轮询用于作业队列（Ops JobsWatch 1s；Brain Jobs 3s + 9 路并行 list_jobs）、Inbox 增强进度（1.5s get_job_progress）、Today 统计/健康（30s）。所有轮询在标签页隐藏时暂停，并用请求序号守卫防止陈旧响应覆盖新响应。

04核心概念体系

理解 GBrain 必须先掌握三组关键概念：Brain/Source 双重路由轴、Trust Boundary（remote/local 信任边界）、以及实体-状态设计方法论。误解前两者会导致查询「静默走错」或数据泄露。

4.1 两个正交组织轴：Brain 与 Source #

Brain — 哪个数据库

你的个人大脑是 host。可通过 gbrain mounts add 挂载额外的大脑（团队发布的，各有独立 DB 与访问策略）。路由：--brain / GBRAIN_BRAIN_ID / .gbrain-mount dotfile。

Source — 数据库里的哪个仓库

一个大脑可含多个 source（wiki、gstack、openclaw、essays）。slug 唯一性是 (source_id, slug) 而非 slug。路由：--source / GBRAIN_SOURCE / .gbrain-source dotfile。

两轴都遵循同样的 6 级解析模式。误路由是「静默」的——查询不报错，只是返回错误库/错误源的结果，这也是为什么 sourceScopeOpts 被设为单一强制通道。

4.2 Trust Boundary：remote vs local #

OperationContext.remote: boolean 是类型上必填的——「类型系统是第一道防线」。语义：remote===false 是可信本地拥有者（OS 即信任边界）；任何不严格等于 false 的值都视为不可信/远程。防御性代码用 ctx.remote !== false（除非显式 false 否则不信任）来防 cast 绕过。

remote 改变行为的实例：get_page 在 remote 时剥离整个 takes fence 并只保留 visibility:'world' 的 facts 行；file_upload 收紧文件系统限制（cwd 锁定）；per-call 搜索 mode 覆盖对远程被忽略（防升级到昂贵的 tokenmax）；__all__/all_sources 跨源仅对可信本地开放。

05搜索与检索机制

混合检索是 GBrain 的技术心脏。入口 hybridSearch(engine, query, opts)（src/core/search/hybrid.ts），管线为：关键词 + 向量 + 关系（+图）→ RRF 融合 → 归一化 → boost → cosine 重打分 → 去重 → rerank → autocut。全程 fail-open。

5.1 四召回臂与融合流程 #

三个返回路径都共享 post-fusion boost + alias-hop + evidence + budget 尾段：(a) 未配置嵌入 provider；(b) 嵌入/向量失败 → 关键词兜底；(c) 完整混合。在 (a)/(b) 下关系臂仍与关键词经 RRF 融合，使类型化边答案在向量不可用时也能存活。

5.2 RRF 融合算法 #

常数 RRF_K = 60；compiled-truth 加成 COMPILED_TRUTH_BOOST = 2.0。实际走的是加权变体 rrfFusionWeighted：

// score(doc) = Σ_lists 1 / (k_list + rank_in_list)，再 min-max 归一，再 compiled-truth ×2.0
for (const { list, k } of lists) {
  for (let rank = 0; rank < list.length; rank++) {
    const rrfScore = 1 / (k + rank);          // 核心 RRF 项 (rank 从 0 起)
    existing ? existing.score += rrfScore      // 跨臂累加
             : scores.set(key, { result, score: rrfScore });
  }
}
const maxScore = Math.max(...entries.map(e => e.score));
for (const e of entries) {
  e.score = e.score / maxScore;               // 归一到 0..1
  e.score *= (e.result.chunk_source === 'compiled_truth' ? 2.0 : 1.0);
}
  • 每臂以 {list, k} 进入融合，k = effectiveRrfK(60, weight) = 60/weight——weight 越高 → k 越低 → 该臂头部贡献越强（如 keywordWeight 1.20 → k=50）。
  • 向量臂：每个扩展查询变体一条 list；关键词臂：一条；关系臂：中性 k=60（竞争但不主导，image 模态排除）。
  • rrfKey = ${source_id}:${slug}:${chunk_id}，含 source_id 使跨源同 slug 页面不塌陷。
  • 图信号不是融合臂，而是 post-fusion 乘性 boost（邻接 hub 1.05 / 跨源 hub 1.10 / session 降权 0.95）。

5.4 语义查询缓存与 knobs_hash #

缓存按查询嵌入的 cosine 相似度命中（非精确文本），默认阈 0.92 / TTL 3600s。行 PK = sha256(sourceId::queryText::knobsHash)。关键防污染机制：knobsHash（KNOBS_HASH_VERSION = 12）把 mode、缓存标志、tokenBudget、expansion、searchLimit、所有 reranker 字段、embedding 列+provider、graph_signals、schema pack 名+版本、contextual_retrieval 档、autocut、relational_retrieval+深度、以及解析后的硬排除前缀列表全部折进 key。因此 tokenmax 写入与 conservative 写入落在不同行，绝不会串味。追加是严格 append-only 并 bump 版本（重排会静默重建所有持久行的 hash）。

SELECT qc.results, qc.embedding <=> $1::vector AS distance ...
FROM query_cache qc
WHERE qc.source_id = $2
  AND qc.knobs_hash = $4                         -- 防跨模式污染
  AND qc.embedding <=> $1::vector < $3            -- distance < 1 - similarity
  AND qc.created_at + (qc.ttl_seconds||' seconds')::interval > now()
  AND <CACHE_GATE_WHERE_CLAUSE>                   -- 两层 page-generation 门
ORDER BY qc.embedding <=> $1::vector LIMIT 1

另有两层 page-generation 门：当底层页面自存储起 generation 已变，缓存行失效。缓存跳过条件：缓存禁用、walkDepth>0、设 nearSymbol、非默认嵌入列、或开启 adaptiveReturn。

5.5 意图分类、扩展、rerank、autocut、boost #

意图分类（零 LLM）

classifyQuery 单次正则产出 5 个正交轴：intent（entity/temporal/event/general）、suggestedDetail、suggestedRecency、suggestedSalience、suggestedModality。意图→权重映射（最大 1.25×，只破平不翻转），如 entity: keywordWeight 1.15、exactMatchBoost 1.25。

多查询扩展

Haiku 把查询改写为 ≤3 变体（仅 tokenmax）。双层消毒：输入 sanitizeQueryForPrompt（剥离注入前缀 ignore/forget/override/system），输出 sanitizeExpansionOutput（去重、去控制符、≤2 备选）。

Rerank（cross-encoder）

默认 zeroentropyai:zerank-2，在 dedup 与 slice 之间。发送 top topNIn 的 chunk_text 给 gateway.rerank()，重排头部、原序补尾（保召回）。Fail-open：任何错误记 JSONL 审计并原序返回。

Autocut（断崖裁剪）

仅在 cross-encoder 的 rerank_score 上运行（RRF 的 rank1→rank2 gap 被实测无区分度）。归一后找 ≥ jumpRatio（0.20）的最大连续断崖并裁剪。alias-hop 注入页受 preserve 保护。仅首页生效。

Recency boost：每前缀半衰期衰减，evergreen 前缀（concepts/、originals/）factor=1.0，daily//chat/ 激进衰减。Salience boost：1 + k·log(1+score)，score = emotional_weight + take_count（对数压缩，界 ~[1.0,1.6]），与 recency 正交。adaptive_return：意图驱动的上限（entity→2，其它→6），是「上限」而非「断崖」（rank-1 在单答案场景 ~94% 正确）。所有 post-fusion boost 共享一个 floorThreshold，防弱重叠候选靠元数据 boost 越级。

信任模型（D11/D12）

6.4 scope 与 localOnly 的远程强制 #

  • localOnly — 结构性排除：const mcpOperations = operations.filter(op => !op.localOnly)。localOnly op 永不出现在 tools/list，调用它返回 unknown_operation。共 8 个 localOnly op（见 §11）。
  • scope — 每请求校验：requiredScope = op.scope || 'read'，hasScope(authInfo.scopes, requiredScope) 失败即 403 insufficient_scope 并记 mcp_request_log；通过才 dispatchToolCall。本地 CLI（remote===false）完全跳过 scope（OS 即边界）。

6.5 Source 绑定与 OAuth 客户端 #

OAuth 客户端行绑定源：oauth_clients.source_id → AuthInfo.sourceId（写权限），federated_read TEXT[] → AuthInfo.allowedSources（读联邦，独立于写源）。读侧全部经 sourceScopeOpts：

export function sourceScopeOpts(ctx) {
  const allowed = ctx.auth?.allowedSources;
  if (allowed && allowed.length > 0) return { sourceIds: allowed }; // 联邦读
  if (ctx.sourceId) return { sourceId: ctx.sourceId };              // 标量
  return {};                                                        // 本地/未设 → 不限
}  // 攻击者传空 allowedSources:[] 不会放大为「全部」——落到标量分支

Thin-client（TTY）：gbrain init --mcp-only 造一个无本地内容、指向远程 gbrain serve --http 的客户端。路由 seam runThinClientRouted 在 connectEngine() 之前检测（isThinClient(cfg)），从不打开空的本地 PGLite；localOnly op 本地以 refuseThinClient 拒绝并给提示。

export function edgeColorVarFor(linkType) {
  if (!linkType) return '--color-hairline';
  let h = 0;
  for (let i = 0; i < linkType.length; i++) h = (h * 31 + linkType.charCodeAt(i)) >>> 0;
  return EDGE_PALETTE[h % EDGE_PALETTE.length];

7.5 代码图（Code Intelligence） #

导入时用 tree-sitter 建边（calls | imports | references），接收者类型解析把 obj.method() 升级为 Class::method。边先未解析发出，落到最内层包含 chunk，持久化到两表：code_edges_chunk（两端已知 chunk）与 code_edges_symbol（目标仅知限定名）。读时 UNION。code_blast/code_flow 走 JS 层 BFS（非 SQL CTE），每深度置信 1/(1+0.3·depth)；code_flow 终端节点经 classifySink 标注 db_call|http_call|file_io|process_exec。

7.6 本体、专家路由、轨迹 #

Ontology 本体

骑在 facts 表上（双时序）。mergeOntologyFact supersede 而非覆盖；findOntologyConflicts 用 HAVING count(DISTINCT value)≥2 AND count(DISTINCT source)≥2 检出真实分歧（不误判时序取代）。

find_experts 专家路由

score = expertise × max(0.1, recency_decay) × (0.5+0.5·salience)，expertise=log1p(hybrid_score)，recency=exp(-days/180)（6 月半衰）。跑 hybridSearch 时关 salience/recency 取干净相关度。

find_trajectory 轨迹

按 valid_from ASC 取类型化 claim；detectRegressions 检连续下跌 ≤ -10%；computeDriftScore = 1 - mean(cosine(emb[i],emb[i-1]))（<3 点为 null）。

08技能系统

Skills 是工具无关的「胖 markdown」文件（skills/<slug>/SKILL.md），本质是喂给 Agent 的操作指令。约 48 个技能通过 frontmatter 的 triggers 做运行时路由，并用「功能域解析器」两层分发压缩路由文件。

8.1 SKILL.md 文件格式 #

每个技能是 YAML frontmatter + 散文正文。正文即 Agent 的操作说明——当它说「search / store / 查」时，Agent 调用本服务器上同名的 MCP 工具。frontmatter 携带 name、description、triggers[]（路由短语）、tools[]（该技能调用的 op）、mutating、writes_to[]（受许可的写前缀）。正文遵循一致性结构：## Contract、## Phases/Workflow、## Anti-Patterns、## Output Format、## Quality Rules。

路由是运行时发现，非表驱动
Agent 遍历每个 SKILL.md，解析 triggers: 数组并对入站消息做子串/语义匹配。RESOLVER.md 里的托管块表格已于 v0.36 退役——路由现居 frontmatter。skills/manifest.json 是机器目录。

8.2 两层分发：功能域解析器 #

09数据库设计

GBrain 在 BrainEngine 抽象之下支持两种引擎：PGLite（嵌入式 WASM Postgres，零配置默认，2 秒就绪）与 Postgres + pgvector（Supabase / 自托管，1000+ 文件推荐）。两引擎锁步（parity）演进，由测试钉死。

9.1 引擎工厂与 BrainEngine 接口 #

export async function createEngine(config): Promise<BrainEngine> {
  const engineType = config.engine || 'postgres';
  switch (engineType) {
    case 'pglite':   { const { PGLiteEngine } = await import('./pglite-engine.ts');   return new PGLiteEngine(); }
    case 'postgres': { const { PostgresEngine } = await import('./postgres-engine.ts'); return new PostgresEngine(); }
    default: throw new Error(`Unknown engine type: "${engineType}"...`);
  }
}  // 动态 import：PGLite 的 WASM 永不为 Postgres 用户加载

engine.ts 定义 interface BrainEngine（~2225 行类型），PostgresEngine（6357 行）与 PGLiteEngine（6098 行）锁步实现。readonly kind: 'postgres'|'pglite' 用于 parity 分支。关键面：生命周期（connect、initSchema、transaction、withReservedConnection、runMigration）、页面 CRUD、chunk/embedding、搜索（searchKeyword、searchVector(Float32Array)）、图/链接/标签/时间线、takes/facts/dream。多数读方法接 opts?:{sourceId?;sourceIds?} 让 sourceScopeOpts 输出直接展开。

9.3 迁移机制 #

MIGRATIONS: Migration[] 是 append-only 数组（「新迁移加到末尾，永不修改既有」），v1 是 schema.sql baseline，LATEST_VERSION 当前 124。

interface Migration {
  version: number;
  name: string;
  sql: string;                                        // 引擎无关
  sqlFor?: { postgres?: string; pglite?: string };    // 引擎特定覆盖（胜出）
  transaction?: boolean;                              // false → 不包事务（供 CONCURRENTLY）
  handler?: (engine) => Promise<void>;                // TS 层数据变换
  verify?: (engine) => Promise<boolean>;              // 可选后置探针
}

CREATE INDEX CONCURRENTLY 需 transaction:false（Postgres 拒绝在事务内建并发索引），仅 Postgres 生效、PGLite 忽略（无并发写者，用 sqlFor.pglite 的普通 CREATE INDEX）。失败的并发索引留下 invalid 残留，由 handler 预删（pg_index.indisvalid）。

9.4 pgvector 与嵌入维度 #

  • 默认文本嵌入 1536d（content_chunks.embedding vector(1536)、takes.embedding），来自 OpenAI text-embedding-3-large。
  • 多模态/图像 1024d（embedding_image、embedding_multimodal，Voyage multimodal-3）。modality 列区分行。
  • 索引：HNSW + vector_cosine_ops（全量 + image 部分索引），takes/facts/query_cache 嵌入亦 HNSW。
  • HALFVEC：pgvector ≥0.7 时用 halfvec_cosine_ops 省空间；PGLite 内置 pgvector 始终 HALFVEC。维度按 embedding_dimensions config（默 1536）在迁移时解析。
  • 嵌入以 Float32Array 跨引擎边界。
JSONB 铁律（Postgres 特有陷阱）
永不 JSON.stringify 进 ::jsonb cast——postgres.js 会双重编码为 jsonb 字符串标量，PGLite 掩盖此 bug（只在 Postgres/Supabase 暴露）。修复：传原始对象给 engine.executeRaw / 用 executeRawJsonb / sql.json()；positional 路径经 $N::text::jsonb。由 check-jsonb-*.sh + DATABASE_URL 门控的 e2e parity 测试兜底。

↻附录 A · Dream Cycle 守护进程

Dream Cycle 是 GBrain 的 24×7 自我增强引擎（src/core/cycle.ts）——夜间自动摄取、增强、整合，让大脑「保持锋利」。ALL_PHASES 定义了完整的相位流水线，按依赖顺序调度。

相位有作用域分类（PHASE_SCOPE）：source（每源）、global（全脑，如 embed/orphans）、mixed。每源 autopilot 只跑 source+mixed 相位，global 相位全脑跑一次。写相位（sync/extract/embed）需 per-source 锁并在相位间 yieldBetweenPhases（穿越 PgBouncer）。预算上限在 budget-meter.ts。相位状态 ok|warn|fail|skipped，本 fork 为 CycleRow 增 phases 字段供 DreamCycleCard 展示各相位耗时。

校准三相位（Hindsight wave）
propose_takes（在 consolidate 后，看到刚整合的 takes 决定还没捕获什么）→ grade_takes（新接受的提案下一 cycle 可评级；不自动接受，用户总是审阅）→ calibration_profile（读新鲜解析，voice-gated 叙述，Haiku 裁判便宜）。
