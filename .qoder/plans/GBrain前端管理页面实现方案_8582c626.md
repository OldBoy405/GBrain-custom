# GBrain 前端管理页面完整实现方案（上游兼容优化版）

## 零、上游兼容性核心策略（必须优先遵守）

### 0.1 项目隔离边界分析

GBrain 项目已天然形成清晰的隔离边界，基于 CUSTOM.md 合并历史（v0.42.56.0 合并 0 冲突）的实际验证：

```
上游核心代码（garrytan/gbrain，合并时必须原样保留）
├── src/core/          ← 绝不能改（operations.ts、引擎、搜索、AI等）
├── src/mcp/           ← 绝不能改（MCP server、dispatch）
├── src/commands/      ← 绝不能改（CLI命令）
├── src/cli.ts         ← 绝不能改
├── src/types/         ← 绝不能改
├── scripts/           ← 除已有二开文件外绝不能改
├── test/              ← 绝不能改已有文件
├── skills/            ← 绝不能改
├── docs/              ← 不修改上游已有文档
└── package.json       ← 仅保留已有二开改动（postinstall），不新增改动

二开隔离区（本方案所有改动严格限定在此范围）
├── admin/             ← 前端SPA（独立子项目）
│   ├── package.json   ← 仅在此文件添加前端依赖
│   ├── src/           ← 所有前端源代码
│   └── dist/          ← 构建产物（必须提交git，二进制嵌入需要）
├── CUSTOM.md          ← 追加每条改动记录
├── docs/operations/   ← 运维文档（已有二开文档目录）
└── .qoder/            ← Qoder 知识模块

自动生成文件（无冲突，由 build:admin 重新生成）
└── src/admin-embedded.ts  ← scripts/build-admin-embedded.ts 从 admin/dist/ 生成
```

### 0.2 八条上游兼容原则的逐一落地

| # | 原则 | 具体落地措施 |
|---|------|-------------|
| 1 | 前端代码独立存放 | 100%代码在 `admin/` 目录内，不修改 `src/`、`scripts/`、`test/` 中的任何现有文件 |
| 2 | 非侵入式API扩展 | 三层策略：优先复用已有 `/admin/api/*` 端点；其次通过已有路由注册机制添加新端点（不修改 operations.ts）；最后采用前端自包含降级（直接调用MCP端点） |
| 3 | 遵循现有架构模式 | Contract-first在前端内部镜像（手写类型mirror，类同 scope-constants.ts 模式）；DESIGN.md设计规范严格执行 |
| 4 | 配置/插件机制集成 | 利用 `admin/package.json` 管理依赖；Vite proxy配置转发API；shadcn/ui `components.json` 配置管理组件 |
| 5 | 标准包管理 | 仅 `cd admin && bun add <pkg>` 添加依赖；仅更新 `admin/package.json` + `admin/bun.lock`；根目录 package.json 不新增依赖 |
| 6 | .gitignore规则 | `admin/dist/` 必须提交（二进制嵌入需要）；`admin/node_modules/` 已在.gitignore；shadcn/ui源码需提交；.gitignore末尾追加admin临时产物规则 |
| 7 | 测试隔离 | 仅在 `admin/` 内用Vitest新增前端测试；不修改 `test/` 目录；每次改动后运行 `bun run test` 确保上游3700+测试通过 |
| 8 | 文档独立维护 | 新增 `admin/docs/` 存放前端专属文档；运维更新 `docs/operations/`；不修改 AGENTS.md、README.md、CLAUDE.md 等上游核心文档 |

### 0.3 上游合并实操流程

**合并前检查**：
```bash
git diff upstream/master --stat
# 期望：仅 admin/、CUSTOM.md、docs/operations/、.qoder/、.gitignore（末尾追加行）
```

**冲突预案（按优先级）**：
1. `src/admin-embedded.ts` 冲突 → 接受upstream版本，重运行 `bun run build:admin`
2. `admin/package.json` 冲突 → 手动合并依赖版本，保留二开新增依赖
3. `admin/src/` 中上游可能新增的文件 → 人工审查，通常接受上游改动
4. `.gitignore` 冲突 → 接受上游版本，末尾追加二开规则
5. 根 `package.json` 冲突 → 接受上游，仅保留postinstall脚本二开改动

**合并后验证**：
```bash
bun run typecheck && bun run test && bun run verify
cd admin && bun run build
bun run build:admin
```

## 二、现代化前端技术架构建议

### 2.1 技术选型（全部依赖添加在 admin/package.json）

| 层面 | 选型 | 上游兼容性 |
|------|------|-----------|
| 框架 | React 19（保持现有） | 上游也用React 19，版本同步 |
| 构建工具 | Vite 6（保持现有） | 仅修改 admin/vite.config.ts |
| 路由 | React Router v7 | 仅admin/package.json新增 |
| CSS方案 | Tailwind CSS v4 | 仅admin/内配置和依赖 |
| 组件库 | shadcn/ui（源码复制模式） | 复制到 admin/src/components/ui/ |
| 图标 | lucide-react | 仅admin/package.json新增 |
| 状态管理 | TanStack Query v5 + Zustand | 仅admin/package.json新增 |
| 表单 | react-hook-form + zod | 仅admin/package.json新增 |
| 图表 | D3.js + Recharts | 仅admin/package.json新增 |
| 前端测试 | Vitest | 仅admin/内配置，不影响上游bun test |

### 2.2 选型核心理由
1. **不引入新框架**：保持React 19 + Vite，不改为Next.js/Astro（Bun兼容性 + 构建嵌入）
2. **Tailwind > 纯CSS**：360行手写CSS将膨胀到2000+；Tailwind JIT只生成用到的样式
3. **shadcn/ui > 自研**：无障碍内置、源码复制不锁定依赖、与项目自包含哲学一致
4. **TanStack Query**：替代useEffect+setInterval轮询，声明式数据获取+缓存策略

### 2.3 向后兼容策略
- admin/目录完全独立，git merge仅package.json依赖版本差异
- 现有Agents/Dashboard/RequestLog/Calibration/JobsWatch页面保持可用
- API层api.ts接口不变，新端点追加
- CSS变量体系平滑过渡到Tailwind theme配置
- dist/仍提交git，build:admin流程不变

## 四、开发步骤与最佳实践

### 4.1 初始化（全部在 admin/ 内操作）

**Task 1：依赖安装**
```bash
cd admin
bun add tailwindcss @tailwindcss/vite react-router-dom @tanstack/react-query zustand lucide-react react-hook-form zod
bun add -d vitest @testing-library/react @testing-library/jest-dom jsdom
```

**Task 2：Tailwind + shadcn/ui + 路由配置**
- admin/vite.config.ts 注册Tailwind + Vitest插件
- admin/tailwind.config.ts 定义设计token
- shadcn/ui init（组件源码生成到 admin/src/components/ui/）
- React Router v7替换hash路由，保留现有页面路由

**Task 3：前端测试基础设施**
- Vitest配置在 admin/vite.config.ts
- 测试文件在 admin/src/**/__tests__/，与上游 test/ 完全隔离
- 每次改动后验证：bun run typecheck + bun run test

### 4.2 核心实现

**Task 4：API类型层**
- admin/src/api/types.ts 手写类型镜像（类同 scope-constants.ts 的 mirror 模式）
- 不直接导入 src/core/ 的类型，避免跨编译边界

**Task 5：TanStack Query hooks**
- admin/src/hooks/ 目录，每个端点一个hook
- QueryClientProvider 在 main.tsx 注册

**Task 6：通用组件库**
- admin/src/components/ui/：DataTable, StatCard, Badge, CodeBlock, EmptyState, StatusDot, FilterBar, Drawer, Modal
- 按DESIGN.md规范实现，全部通过可访问性检查

**Task 7：页面实现**
- 每个Page是feature组件的薄组装层
- 导航配置化：lib/routes.ts 配置数组驱动侧边栏

### 4.3 最佳实践（上游兼容增强）
1. 类型手写mirror，不导入 src/core/
2. 前端测试用Vitest在admin/内，不影响bun test
3. 每次改动后跑 bun run test + bun run verify
4. CUSTOM.md 每个阶段完成后追加记录

## 五、后端API集成方案（三层非侵入策略）

### 第一层：复用已有端点（零改动）
直接使用 /admin/api/stats、/admin/api/agents 等现有端点

### 第二层：利用已有路由注册机制（最小改动）
如 admin HTTP server 有动态路由注册，在不修改 operations.ts 前提下注册新端点（实现阶段分析 serve-http.ts 后确定）

### 第三层：前端自包含降级（零后端改动）
- 内容入库/精确检索：前端直接调 /mcp HTTP端点
- 技能进化：前端fetch skills/manifest.json
- 三大范式：纯静态页面

### 数据流
```
React组件 → TanStack Query hook → api.ts fetch
  → /admin/api/* (已有端点) 或 /mcp (JSON-RPC降级)
  ← JSON响应 ← TanStack Query缓存 ← React渲染
```
